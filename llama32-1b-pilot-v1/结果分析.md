# Llama-3.2-1B-Instruct 最后一层 FFN 裁剪小规模验证

单张 RTX 4090，BF16、FlashAttention 2；双方开启 breakable Prefill CUDA Graph，关闭前缀缓存。
性能为真实权重下离线 `LLM.generate` 的端到端耗时，输出 1 token；不含模型加载、Graph 捕获和预热。
每格记录 7 次测量，表中为耗时中位数；变化为负表示改善。

正确性：16/16 条生成序列 token 完全相同；vLLM 默认 `check_logprobs_close` 对照通过。
请求 prompt logprobs 时确认未启用裁剪，对照检查通过。

## 验收与实现

- 原生 `LlamaForCausalLM`，16 层；双方均启用 breakable Prefill Graph，torch compilation 关闭。
- 本地实验分支 `codex/last-layer-ffn-llama-pilot`，基于 `0a14d0ddf132388555e8e17e5d5866598ed4f541`。未 push，未修改已推送的 Qwen 分支。
- Llama Eager、Graph、缓存前缀和分块 Prefill 四项真实模型回归全部通过（357.92 秒），开启 `VLLM_GPU_SYNC_CHECK=error`；prompt logprobs 回退对照也通过。
- 每格 2 次预热与 7 次测量的总裁剪行数精确等于 `9 × 请求数 × (输入长度 − 1)`，确认覆盖了全部请求的完整 Prefill。
- 表格的 1/4 表示每次 `LLM.generate` 提交的请求数，不是强制的 GPU batch size。计数显示，裁剪版单请求组每格执行 9 次 Prefill，四请求组每格执行 18 次 Prefill，即每次四请求调用被分成两次模型执行。不能把这张表描述为固定 GPU batch 4 的单次 kernel 测量。
- GSM8K 固定前 32 题、5-shot、greedy、最多 1024 输出 tokens：双方均为 8/32（25%），无无效答案。这是小样本回归检查，不代表模型全量 GSM8K 准确率。
- GSM8K 逐题生成 token 序列一致：32/32。

## 初步判断

8 个测试点的耗时中位数均下降。4096 tokens 的两档请求数，以及 2048 tokens / 四请求组，下降约 4.2%–4.4%，高于此前 Qwen2.5-7B 小规模对照的约 2.4%–2.7%。这支持该优化能在原生 Llama 路径生效。

Llama-3.2-1B 的层数较少，最后一层 FFN 在总计算中占比可能更高，这与较大的收益方向一致；它不是本轮通过 profiling 得出的严格归因。小模型的短输入更容易受到 CPU 和调度开销影响，各点收益并不严格随输入长度单调增长。

本轮仅做一对原路径/裁剪运行，每格 7 次测量；没有做跨进程 ABBA 复测或 HTTP serving 性能对照。这里的 4% 左右是预热后的离线生成耗时改善，不应直接写成所有在线服务场景的吞吐提升。
